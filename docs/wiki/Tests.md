# Tests

## Tests unitaires et d'intégration

```bash
npm test
```

`npm run test:vigie` fait tourner la même suite avec une Vigie simulée (`TEST_AVEC_VIGIE=1`) : le site doit s'y comporter exactement de la même façon (la Vigie est facultative). `test/vigie-emission.test.js` couvre l'émission elle-même (événements, signature, tampon, budget, comptes, retrait) ; `test/vigie-service.test.js` le service de la Vigie (réception, chaîne, décisions, Zitadel avec une API simulée, ligne de commande, sauvegarde) et un essai de bout en bout : une vraie Vigie sur un port local, le site qui lui envoie ses lots et applique ses décisions ; `test/vigie-moteur.test.js` le moteur d'entités (quorum, décroissance, exceptions à source unique, modes, réponses automatiques, reprise, ligne de commande) ; `test/vigie-regles.test.js` les règles Sigma (modificateurs, conditions, règles mal écrites, couverture de DS1 à DS31), les corrélations, les détecteurs, les listes de menaces et le contrôle des rôles sur une vraie base du site. `test/vigie-console.test.js` couvre la console (phase D3a) : jeton Cloudflare Access (signature, émetteur, audience, dates, algorithme, rotation des clés), 403 sans lui partout, connexion Zitadel (PKCE, state à usage unique, second facteur, rôle `vigie.*` de la bonne organisation), sessions (identité Access, 15 min, 1 h, rafraîchissement), plafond relu toutes les 5 minutes et avant une action, droits à deux clés et amorce, CSRF, ré-authentification par le même compte, DS29 et DS30 ; `test/vigie-console-vues.test.js` les gabarits (aucun style ni script en ligne, échappement, adresses tronquées pour un Lecteur) ; `test/vigie-console-alertes.test.js`, `test/vigie-console-evenements.test.js` et `test/vigie-console-sante-flux.test.js` les écrans de lecture (droits, adresses tronquées, échappement, 404, plans de requête sur index, pagination sans trou, CSV neutralisé et noté, flux aux sommes conservées et barre de la vue d'ensemble aux mêmes nombres) ; `test/vigie-console-actions.test.js` et les tests des écrans `decisions`, `reglages`, `droits` les actions (droit de l'action, ré-authentification, garde-fous partagés avec la ligne de commande, message et redirection, formulaires extraits des pages rendues puis postés, erreurs près du bon champ, valeurs reprises et échappées). `test/console-env.js` fournit l'environnement commun (faux Cloudflare Access, faux Zitadel, connexion).

Les tests BV-33 complètent `test/vigie-emission.test.js` (catégories et volumes, listes, absence de contenu, HEAD/refus), `test/chiffrement.test.js` (isolation des compteurs concurrents), `test/vigie-dossiers.test.js` (enjeu, seuil par session, relectures de listes, trois réseaux, fusion/scission/purge) et `test/vigie-console-evenements.test.js` (lecture échappée, masquage, droits et CSV). Ils réutilisent les serveurs et bases jetables existants.

Les tests LEG-V3 de `test/vigie-dossiers.test.js` vérifient le masquage des graines, titres, notes et cibles, les IPv6 accolées ou anciennement mal tronquées, les collisions d’entités et leurs références, les stocks de plus de 1 000 dossiers, la priorité aux nouvelles adresses échues, la reprise transactionnelle et les fusions/scissions après purge. Le masque est partagé avec les écrans de la console.

Ils utilisent `node:test`, sans dépendance supplémentaire, et prennent environ 40 s. Chaque test travaille dans un dossier temporaire avec sa propre base. Le jeu de démonstration n'est généré qu'une fois par fichier, puis recopié pour chaque test.

### Tests de durée

La machine de développement est souvent chargée (plusieurs agents en parallèle : charge de 60 à 95 sur 16 cœurs). Un seuil en millisecondes y échoue au hasard, puis passe relancé seul. Règle : **mesurer le travail ou comparer des durées relatives ; jamais un seuil absolu seul.** Dans l'ordre de préférence :

1. **Durées relatives** : une saisie hostile contre une saisie ordinaire, 8 000 signes contre 1 000, une requête piégée contre la même requête sans piège. Un défaut (retour arrière d'une expression régulière, boucle quadratique) change le rapport d'un ordre de grandeur ; la charge, qui touche les deux mesures, ne le change pas.
2. **Compter le travail** plutôt que l'horloge (appels, pas) : par exemple un `Set` qui compte ses `has()` pour les ancres d'intertitres (linéaire : au plus 2 par ancre).
3. **Meilleur de N essais** (`meilleur()`, `meilleurAsync()` de `test/duree.js`) : la charge ne fait qu'allonger une mesure, jamais la raccourcir.
4. **Un seuil multiplié**, justifié en commentaire par la durée du défaut mesurée, seulement si rien d'autre ne marche.

Une **attente** n'est pas une mesure : on interroge jusqu'à une échéance large (`attendre()`, 30 s), jamais un nombre fixe de tentatives ni un délai fixe, et on libère les tâches simulées par une barrière plutôt que par une minuterie. Chaque test de durée doit encore échouer quand on réintroduit le défaut qu'il garde : on le vérifie en le réintroduisant dans une copie, puis on rétablit.

## Tests navigateur (Playwright)

Ils tournent dans le **conteneur officiel Playwright** (`mcr.microsoft.com/playwright`, même version que `@playwright/test` dans `e2e/package.json`), contre un serveur **déjà démarré**, et n'installent rien sur la machine (il faut Docker).

```bash
# lecture seule : site public et écrans de l'admin
BASE_URL=http://<hôte>:<port> E2E_LOCAL_AUTH=<LOCAL_AUTH_TOKEN du serveur> npm run e2e
# avec les parcours qui modifient les données (serveur de test jetable)
BASE_URL=… E2E_LOCAL_AUTH=… E2E_ALLOW_WRITES=1 npm run e2e
# un seul projet, ou un seul test (options passées à « playwright test »)
BASE_URL=… E2E_LOCAL_AUTH=… npm run e2e -- --project=iphone
BASE_URL=… E2E_LOCAL_AUTH=… npm run e2e -- -g "statistiques"
```

`npm run e2e` appelle [`e2e/run.sh`](https://github.com/Volfieldd/deux-regards/blob/main/e2e/run.sh), qui lance le conteneur (`--network host`, sous votre utilisateur), y fait `npm install` dans `e2e/`, puis `npx playwright test` avec les options reçues.

| Variable | Défaut | Effet |
|---|---|---|
| `BASE_URL` | `http://localhost:3000` | serveur testé |
| `E2E_LOCAL_AUTH` | — | jeton de la connexion locale de test du serveur (`LOCAL_AUTH_TOKEN`). Sans lui, tous les tests de l'admin sont ignorés. |
| `E2E_ALLOW_WRITES` | — | `1` : active les tests qui **modifient les données** (projet `parcours`, captures d'import, changement de série sur iPhone, galeries privées) |
| `E2E_CAPTURES` | — | `1` : active les projets `captures-*` |
| `E2E_AUDIT` | — | `1` : active le projet `audit` |

Le serveur testé doit avoir le jeu de démonstration (`npm run seed`) et `LOCAL_AUTH_TOKEN` défini, donc être en HTTP et hors production.

- **Données :** `parcours` **modifie les données**. Il ne suppose rien du contenu, nettoie les restes d'un passage interrompu, puis restaure à l'identique les réglages d'images trouvés (même en cas d'échec). À réserver à un serveur de test.
- **Accessibilité :** axe-core (WCAG 2.2 A/AA) sur les pages publiques ; pour l'admin, **aucune violation tolérée**, en mode sombre **et** en mode clair, sur ordinateur et sur téléphone.
- **Temps :** le diaporama est testé avec l'horloge simulée de Playwright (pas d'attente réelle).
- **Erreurs :** toute erreur JavaScript, toute violation de la politique de sécurité du contenu et toute ressource en échec fait échouer le test.
- **Résultats :** captures et traces (conservées en cas d'échec) dans `e2e/results/`, rapport HTML dans `e2e/report/`.

### Limites connues

- **Droits sur `e2e/` :** le conteneur tourne sous l'utilisateur qui lance `run.sh` et fait `npm install` dans `e2e/` (monté en `/e2e`), puis y écrit `results/` et `report/`. Si cet utilisateur ne peut pas écrire dans `e2e/` (dépôt cloné par un autre compte, `e2e/node_modules` créé par un autre utilisateur), l'installation échoue avant le premier test. Donnez-lui les droits d'écriture (`chown` ou groupe commun), ou lancez depuis votre propre clone.
- **Test `statistiques` en parallèle :** il compte les visites publiques avant et après sa propre visite. Quand tous les projets tournent en même temps, d'autres tests visitent le site public au même moment et faussent le compte : il peut échouer, alors qu'il passe seul (`npm run e2e -- --project=desktop -g statistiques`). À rendre indépendant des visites parallèles (voir la feuille de route de `PLAN.md`).

`e2e/tests/edition-photos.spec.js` couvre les admins v1 et v2 : demande de description sans perdre les saisies, confirmation du remplacement, annulation et Défaire ; aperçu du filigrane sur place sans écriture et erreur de rendu ; choix des six compositions dans le bandeau sans changer la vue du visiteur. Serveur jetable, `E2E_ALLOW_WRITES=1`, descriptions activées (modèle local ou modèle factice de `test/helpers.js`).
